# The record: a signed statement of one machine's results

**Status: normative. Pinned in `reticuli.toml`; editing it moves the repository
root, so a change is an identity-bearing transition rather than an ordinary
edit. The three questions the first draft left open were decided on 2026-09-16
(see Decisions).**

A **record** is a small JSON document stating what one machine established
about one claim at one time: the identity it recomputed, the implementation
bytes it found, the gate results it obtained by running them, and the
production cost, where one was measured. A record is produced once, signed,
and read many times — by `crosscheck` in place of a claim directory it cannot
reach (a CI run that has ended, another person's machine), and by any external
tool that wants the results without parsing this tool's internal files.

The record is the only file this project promises other programs may parse.
Everything else under `.reticuli/` — the manifest, the ledger — is internal:
readable, but its layout may change in any release. The reasons are the usual
ones for an interface boundary. Any file a third party parses becomes a public
interface whether or not one was declared, and freezing the internal files
would make every field of the bookkeeping a compatibility commitment. And a
signature is only as meaningful as the agreement about what the signed bytes
say: signing an unspecified format makes verification depend on the internals
of the implementation that produced it. So the internals stay private, and
this one document — derived from them, versioned, and specified here — is what
gets signed and exchanged.

## Precondition

A record may be produced only when the claim's identity holds: the bytes
present recompute to the sealed root. A claim that fails `verify` gets a
refusal, not a record — a record is *about* a root, and if the bytes do not
hash to one there is nothing to be about. Gate failure is the opposite case: a
record whose gates failed is valid and worth keeping (a failed rebuild is
evidence about the claim), and states the failure plainly.

## The document

Version 1 is a JSON object with exactly the members below and no others.
Members marked optional may be absent; no other member may be present.

| member | type | required | meaning |
|---|---|---|---|
| `record` | integer | yes | format version of this document; this spec defines version 1 |
| `name` | string | yes | the claim's name, from its recipe |
| `root` | string | yes | 64 lowercase hex — the identity recomputed from the bytes present (`spec/identity.md`) |
| `build_digest` | string | yes | 64 lowercase hex — the digest of the generated bytes present (`spec/identity.md`); the digest of the empty list when none exist |
| `gates` | array | yes | one entry per gate step, in recipe order (see below) |
| `cost` | object | optional | measured production cost totals (see below) |
| `producer` | object | optional | declarations about who produced the generated bytes (see below) |
| `environment` | object | yes | `platform`, `machine`, `runtime` — strings describing the host that produced the record |
| `when` | string | yes | UTC time of recording, `YYYY-MM-DDTHH:MM:SSZ` |
| `tool` | string | optional | the implementation that wrote the record; diagnostic only, carries no meaning |

Each entry of `gates`:

| member | type | meaning |
|---|---|---|
| `output` | string | the output the gate pins, from the recipe |
| `status` | string | one of `ok`, `failed`, `timeout`, `mismatch`, `environment` — the audit vocabulary, unchanged |
| `sandbox` | string | one of `none`, `seatbelt`, `bubblewrap`, `inherited` — what confinement the gate ran under |

Per-gate wall-clock is deliberately **not** a member. The comparison never
reads it — only production cost is compared — and it is the one value that
would change on every re-measurement of otherwise identical facts. Where an
implementation reports gate timings, it does so beside the record, unsigned
and unspecified, so timings can be regenerated or dropped without touching a
signature. A `timeout` status is meaningful without a number: the ceiling that
applied comes from the claim and the environment.

`cost` holds any subset of exactly four keys, each a non-negative number and
never a boolean:

| key | meaning |
|---|---|
| `usd` | money spent producing the generated outputs |
| `tokens` | model tokens spent producing them |
| `calls` | producer invocations |
| `seconds` | wall-clock of production, measured by the machine that ran the producer |

Two rules give `cost` its meaning. First, it is the cost of **producing** the
generated bytes, not of running the gates for this record — gate runtime is
outside the document entirely. Second, **an absent key means unmeasured, and unmeasured
is never written as zero**: a machine that did not meter tokens omits
`tokens`, so a reader can always tell "free" from "unknown". The cost
*commitment* — the envelope, in usd — lives in the claim's recipe, inside the
root; the record only reports measurements to compare against it.

`producer` holds declarations, relayed as given:

| member | type | meaning |
|---|---|---|
| `vendor` | string | who ran the producer (e.g. an API vendor) |
| `model` | string | the model or tool that generated the bytes |
| `blind` | boolean | whether the producer's workspace excluded the generated outputs |
| `cutoff` | string | the producer's declared training-data cutoff, `YYYY-MM` |

## Example

Hashes shortened for display; a real record carries all 64 characters.

```json
{
  "record": 1,
  "name": "toml-1.0.0",
  "root": "b76212b1d2bf…",
  "build_digest": "4530ed4e83…",
  "gates": [
    {"output": "TOML_OK", "status": "ok", "sandbox": "bubblewrap"}
  ],
  "cost": {"usd": 3.40, "tokens": 1084211, "calls": 9, "seconds": 731.2},
  "producer": {"vendor": "openai", "model": "gpt-5", "blind": true, "cutoff": "2026-03"},
  "environment": {"platform": "linux", "machine": "x86_64", "runtime": "CPython 3.13.2"},
  "when": "2026-09-16T20:14:03Z",
  "tool": "reticuli 2.1"
}
```

## Canonical bytes and the record digest

The canonical form of a record is the same serialization the identity uses:
`json.dumps(record, sort_keys=True)` with **default separators** (`", "` and
`": "` — not compact), ASCII escaping of non-ASCII characters, encoded UTF-8.
The **record digest** is the lowercase hex SHA-256 of those bytes; it is what
a signature covers and how a record is cited.

## Signing

A record is signed with the existing ssh mechanism (`ssh-keygen -Y`) over its
canonical bytes, as a detached signature, in a namespace of its own:

    reticuli.record

The namespace is distinct from `reticuli` (attestation) and `reticuli.mint`
(authorization) for the same reason those two are distinct from each other: a
signature made for one purpose must not be presentable for another. A record
signature states "these are the results I obtained"; it must never authorize
an implementation.

Trust is verifier-relative, as everywhere in this tool: a record's signature
means something only against a key in the verifier's own `allowed_signers`.
Other signing mechanisms (for example, a CI platform's identity service) may
wrap a record, and must sign the same canonical bytes, so that one document
has one digest under every wrapper.

## Semantics

**Established versus relayed.** `root`, `build_digest`, `gates`, and
`environment` are established by the recording machine: it computed the hashes
and ran the gates. `cost` and `producer` are relayed: the recording machine
read them from its own bookkeeping, which was in part written from
self-reports. A verifier may treat the first group as "what the signer did"
and must treat the second as "what the signer was told", except
`cost.seconds`, which the recording machine measures itself.

**A record has no role.** It does not say "I am the original" or "I am the
rebuild". Roles exist only in composition: whoever runs `crosscheck` assigns
records to the three positions, and every comparison — same root, same build
digest (byte reuse), different build digest (distinct bytes), cost within the
envelope — is computed from the records' contents. A record therefore cannot
misstate its role; it can only misstate facts, which redoing detects.

**One predicate, two transports.** `crosscheck` over records must reach
exactly the verdict it would reach over the claim directories the records were
produced from. A record is a frozen input to the existing comparison, not a
second definition of it.

**Publishing a record is the call.** An open invitation to rebuild a claim is
announced by publishing a signed record of the original. That record's `when`
is the call's publication date — the date a verifier compares a rebuild's
`producer.cutoff` against. The contamination question ("could this producer
have seen the original?") is thereby answered by comparing two fields of two
signed documents, and a call cannot be anonymous, because a record cannot be
unsigned.

**A proof built from records names its records.** When a three-machine
comparison is satisfied over records rather than directories, the recorded
proof carries the record digests and signer identities it consumed, however
the implementation stores them. The verdict is the same predicate either way;
what differs is whose executions the evidence rests on, and the proof
preserves exactly that — a reader can walk from the proof to the signed
statements behind it.

## Validation

A reader refuses, in band and with a reason, any of: a document that is not a
JSON object; a `record` version newer than it understands (naming the version,
so the failure is a sentence rather than a guess); a missing required member;
a member this spec does not name; a `root` or `build_digest` that is not 64
lowercase hex characters; a `status` or `sandbox` value outside the
vocabularies above; a cost value that is boolean, negative, or not a number.
The member set is closed on purpose: extension is a version bump, not a quiet
extra field under an old version number.

## What a record does not establish

A record proves that its signer asserted these results — nothing more.
Verdicts are earned by running gates; a record is someone else's earned
verdict, relayed with a signature, and the only way to promote it to your own
knowledge is to obtain the bytes and redo the audit. The `producer` block is
testimony even relative to the signer. `when` is the signer's clock. A record
from a key you have not anchored is a document, not evidence.

## Decisions (2026-09-16)

- **The envelope's unit of commitment is usd**; records report whatever units
  were measured, and the comparison prefers the strongest unit both sides
  share, as `crosscheck` already does.
- **The internal files stay private.** The record is the interface; the
  manifest and ledger may change layout in any release. The four cost keys are
  the one part of the internal vocabulary this spec fixes, because the
  comparison is defined over them.
- **The public member names use plain words** (`sandbox`, not the internal
  name for the same value), and the vocabulary of values crosses unchanged
  from the audit, which already has one.
- **Publishing a record is the call.** No fourth document type: the open call
  is the original's signed record, and its `when` is the publication date a
  verifier compares `producer.cutoff` against.
- **A proof built from records embeds them.** Record digests and signer
  identities land in the proof, so provenance is walkable from a verdict to
  the signed statements it rests on.
- **Per-gate wall-clock is outside the canonical bytes.** The comparison never
  reads it; implementations may report timings beside the record, unsigned and
  unspecified. Production cost stays inside, `cost.seconds` included.
