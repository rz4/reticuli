# What a claim proves, and what it does not

*Informational in form, but part of the security contract in substance. It
states what a verdict does and does not establish, and what the sandbox does
not confine. Read it alongside [`spec/verification.md`](https://github.com/rz4/reticuli/blob/main/spec/verification.md)
and [`SECURITY.md`](https://github.com/rz4/reticuli/blob/main/SECURITY.md).*

Read this before trusting anything this tool prints. It is short on purpose.

## The one-sentence version

A claim proves that this artifact satisfies these acceptance criteria, and
gives you a measurement of how strong those criteria are. It does not prove
the artifact is correct, safe, or free of anything.

## What is actually established

**Identity.** The root is a hash over the acceptance tests, the pinned test
data, the recipe, and the recorded verdicts, deliberately excluding the
implementation. Two people holding the same root are holding the same
criteria, and each can check that locally. Changing a test changes the root,
so criteria cannot be weakened silently.

**Earned verdicts.** `audit` re-executes the gates rather than trusting a
stored result. A claim that says "tests passed" has to demonstrate it again,
in a sandbox, on the bytes present.

**Reconstruction, when measured.** If an independent producer regenerates the
implementation from the pinned inputs alone and lands on the same root, the
tests determine an implementation rather than merely accompanying one.

## What is not established

**Correctness.** The criteria are whatever someone wrote. A claim over three
assertions is satisfied by any program that passes those three assertions.
See [`examples/weak/`](https://github.com/rz4/reticuli/blob/main/examples/weak/README.md),
where two implementations with different behaviour carry the identical root
and differ on inputs no test names.

**Safety, or the absence of malice.** A backdoored implementation that passes
the tests is admitted. The generated bytes are outside the root by design, so
the root says nothing whatsoever about them. If you need to know that a
specific binary is the one you audited, what you want is the build digest and
a signature over it, not the root, which is deliberately indifferent to the
implementation.

**That tests were written independently of the code.** The circularity check
refuses a gate whose deciders are all generated, which rules out the crudest
self-certification. It cannot tell whether a human fitted tests to an
implementation, or a model wrote both in one pass with the tests shaped by
the code. Mutation adequacy and held-out evaluation measure that; they do not
prevent it.

**Independence of producers.** This is recorded as a declaration and never
proven. N-version programming assumes independently built versions fail
independently; Knight and Leveson showed that is false even for separate
human teams, and models share pretraining corpora. Two vendors is evidence,
not proof.

**Anything about the host.** A gate runs sandboxed where the platform
supports it, using macOS seatbelt or Linux bubblewrap, probed functionally.
The sandbox confines writes to the gate's workspace and denies the network.
It does not confine reads: a gate can read any file the invoking user can
read, because the scrubbed environment keeps inherited secrets out of its
variables rather than off the disk. A second, strict tier is `audit`'s
default for the receiving posture. It runs a stranger's gates with the user's
own files masked as well, reading back only the workspace and the
furnished-environment cache, and applies a per-file growth ceiling.
`--no-strict` relaxes it to the plain sandbox when you are re-earning your
own work. System paths stay readable under strict, which is what keeps it
robust enough to be the default, so treat it as protection against a gate
exfiltrating your documents rather than as a container. Where no sandbox
exists, that fact is recorded rather than faked and the gate still runs. A
gate is arbitrary code you chose to execute.

On Linux the jail additionally unshares the PID and IPC namespaces and starts
a new session where the host permits it, probed as a unit like the sandbox
itself, with `sandbox_hardened()` reporting whether it applied. Without the
PID namespace the jail's `/proc` is the host's, so a gate could read
`/proc/<pid>/environ` of any process sharing its uid, including the `ret`
that spawned it, which holds a vendor credential for the length of a rebuild.
The environment scrub keeps inherited secrets out of a gate's own variables;
until 2026-10-29 they could walk back in through the filesystem, which made
the scrub decorative on exactly the platform where CI runs. The strict tier's
mask is likewise derived from where this host actually keeps home directories
rather than from the literals `/home` and `/root`, which masked nothing on a
cluster or NFS layout while still reporting `strict`.

**The producer sits outside all of this, by design.** `rebuild` runs the
producer unjailed because it has to reach a model over the network with a
credential, and `criteria/build_check.py` pins that as the contract. The gate
a producer runs while it iterates is confined like any other gate. It was not
until 2026-10-29, which meant the verb aimed at other people's claims was the
one that ran their shell commands with the operator's full standing.

The one confinement a producer CAN receive is the one the caller asks for:
`rebuild --jail` runs it under the generation jail (`_kernel/jail.py`), which
denies reads of the source claim — the answer sheet a "blind" rebuild would
otherwise be free to copy — and of any `--forbid` root, and nothing else:
network, HOME, and credentials stay the caller's, so the freedom contract
above is about the default and is unchanged. The jail refuses where no
backend applies rather than reporting a confinement it did not deliver, and
on hosts that log denials it ledgers a touch receipt of every out-of-room
access the producer attempted. See
[`SECURITY.md`](https://github.com/rz4/reticuli/blob/main/SECURITY.md) for
what remains yours to accept: the
agent-CLI adapters bring their own sandbox rather than this one, and a
recipe's `guidance` reaches the model unescaped.

## Trust boundaries

| you must trust | you need not trust |
|---|---|
| the acceptance tests and pinned data (they are the specification) | the implementation's author |
| the machine you verify on, and this tool running on it | the claim's author's report of what happened |
| the signing keys in your own `allowed_signers` | any signature from a key you have not anchored |
| your producer, if you run one (it executes on your machine) | the producer's self-reported cost — wall-clock is measured locally |

The design moves trust out of testimony, meaning "I tested it", and into
criteria you can read and re-run. It cannot move trust out of the criteria
themselves. If the tests are weak the claim is weak, and the honest response
is to measure the weakness rather than assume it away.

## Failure modes worth knowing

**A passing gate on a thin suite.** This is the most common case and the least
dramatic, and `ret assess` exists for it. A high mutation score on a small
program is not comparable to one on a large program, which is why the report
prints sample sizes.

**A failed reconstruction read as "the tests are weak."** Four causes are
consistent with that observation: a broken producer, an under-specified
suite, a harness mismatch, or a producer too weak for the task. The harness
case came up twice in one afternoon while this was being built. The report
lists all four rather than inviting the flattering reading.

**Mistaking identity for health.** `verify` says the bytes still hash to the
sealed root, and runs nothing. `audit` runs the gates. A claim can verify
perfectly while being thoroughly broken, which is why the two verbs are
separate and named differently.

**Tooling that reformats a sealed claim.** A formatter or import sorter run
over pinned files does not tidy the claim, it renames it, orphaning every
proof and signature that pointed at the old root. Linting is configured to
skip sealed directories, and verification is the backstop.

## Scope

This is a research tool. It ships two independent implementations of the
identity computation, `reticuli.kernel` and `reticuli.reference`, and one of
everything else; the claim format has moved to 4. Its examples are small, no
performance work has been done — every audit re-runs everything — and it has
been exercised on macOS and Linux only.

On compatibility it defers to [`compatibility.md`](compatibility.md), which
is the authority. The format promise stands as of v2.0.0: formats are
append-only, past formats stay readable, and the identity computation changes
only with a format bump and an attested migration. Until 2026-10-29 this
paragraph said there was no compatibility promise yet, which contradicted
that page while the README listed the two side by side as the contract, so a
reader could not tell whether the promise bound. It does. What remains pre-1.0
is everything outside the format: the CLI's surface, the Python API, and the
tool's own claim root, none of which carry a stability guarantee.
